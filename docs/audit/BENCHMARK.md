# 同领域对标报告

> 对标时间：2026-10-29。数据取自各项目 GitHub 主页（星标数为抓取当日页面所示）。
> 目的不是"比谁功能多"，而是回答一个问题：**知客真正的优势在哪、哪些优势其实没落地、哪些劣势必须补**。

## 一、项目定位（先定义再对比）

知客不是通用 Agent 平台，也不是客服 SaaS。它的定位是：

> **可自托管的个人助理 Agent 底座，以 IM（QQ）为主战场，把「记忆 + 提醒 + 工具执行 + 权限审计」做成一个能长期挂在群里的东西。**

四条不可替代的能力（其它项目要么没有，要么不是这个形态）：

1. **单进程可跑 + 无 LLM Key 也能用**：规则 ReAct + 知识库兜底，1 核 1G 可部署；Dify/Open WebUI 类项目空模型即不可用。
2. **IM 原生人格与群聊礼仪**：猫娘「零」、群黑话沉淀、表情包/语音收发、乒乓循环护栏、拟人节奏与群节流——这些是运营出来的，不是框架给的。
3. **动作权限分级 + 哈希链审计**：L0/L1/L2 × T0–T3 的矩阵、L2 强制人工审批、SHA-256 审计链可校验。开源 IM bot 里极少见。
4. **中文小库检索的最优性价比**：FTS5 BM25 + 可选 BGE 向量 + RRF 融合，14 条 KB 也能答准，不需要向量数据库。

## 二、七个对标对象（按形态分组）

### A 组：Agent / 工作流平台

#### 1. Dify（langgenius/dify，约 160k stars）

- **定位**：LLMOps 平台，可视化编排 + Agent + RAG + 插件市场。
- **架构**：Python 后端 + Next.js 前端 + Celery/Redis + PostgreSQL + 向量库，多容器。
- **强项**：可视化 workflow 画布；Agent 独立沙箱可装软件；Marketplace 插件生态；观测接 Langfuse/Opik/Phoenix；BaaS API。
- **弱项**：部署重（PG+Redis+向量库+worker）；IM 渠道靠社区插件，QQ 群体验远不如原生网关；空模型不可用。
- **与知客的关系**：**不同物种**。知客是"一个能长期挂在群里的助理"，Dify 是"给团队搭 AI 应用的工厂"。
- **可借鉴并已落地**：标注回复（annotations）、应用日志与性能观测（本轮补齐 Prometheus 直方图 + 请求 ID）。
- **明确不追**：可视化画布——个人助理场景不需要，做了反而是负担。

#### 2. FastGPT（labring/FastGPT，约 30k stars）

- **定位**：知识库问答 + 可视化 Flow 编排。
- **强项**：知识库分块可逐块编辑/删除；混合检索 + 重排；双向 MCP；文件格式覆盖广（TXT/MD/HTML/PDF/Docx/PPTX/CSV/XLSX/URL）。
- **弱项**：同样是重部署；无 IM 原生能力；无动作权限分级。
- **可借鉴并已落地**：文档导入管道的分块策略（标题优先 + 句级打包）、试召回端点（`/api/kb/test`）——知客原本就有，本轮把 KB 层抽成可单测模块。
- **差距**：FastGPT 支持重排模型（rerank），知客只有 RRF。**本轮未补**：rerank 需要额外模型服务，与"1 核可跑"定位冲突，列为可选依赖更合适。

### B 组：IM Bot 框架（最直接竞品）

#### 3. AstrBot（AstrBotDevs/AstrBot，约 44.6k stars）

- **定位**：多平台 IM 聊天机器人框架 + Agent。
- **架构**：Python，插件化适配器（QQ/OneBot/Telegram/企微/飞书/钉钉/Slack/Discord/LINE/KOOK 等 15+ 平台），1000+ 插件市场。
- **强项**：平台覆盖碾压级；插件生态；Web 管理面板；知识库 + MCP + Skills；沙箱执行。
- **弱项**：插件质量参差；默认人格与群聊运营能力弱（更偏"框架"）；权限模型是插件自理，无统一 L0/L1/L2 审计链。
- **与知客的关系**：**最直接竞品**。知客在"平台数量"上必输，但在"单群深度运营 + 权限审计 + 开箱人格"上领先。
- **本轮已补的差距**：预设角色体系（15 个，AstrBot 只有简单情景预设）；免 Key 搜索（AstrBot 需配 provider）。
- **仍未补**：插件市场。**判断：不做**——个人助理不需要 1000 个插件，需要 40 个真能用的工具（知客已有 42 个）。

#### 4. LangBot（langbot-app/LangBot，约 18.6k stars）

- **定位**：LLM 原生即时通信机器人平台，强调 Multi-Pipeline。
- **强项**：一个实例跑多个不同场景的 bot（Multi-Pipeline 架构）；10+ 平台；MCP 一等公民（内置 `/mcp` 端点、`lbctl` CLI、in-repo skills）；生产特性（访问控制、限流、敏感词、监控）。
- **弱项**：Agent 多步执行深度不如知客（无预算/审批矩阵）；无审计哈希链。
- **与知客的关系**：形态最接近的竞品之一。**它的 Multi-Pipeline 是知客缺的**：知客一个进程只有一套人设（虽然已有角色卡按会话绑定）。
- **本轮已补**：预设角色 15 个 + `POST /api/personas/{id}/apply` 一键切换；角色卡按 chat_key 绑定（原有能力，本轮未动）。
- **差距确认**：真正的"多 pipeline 并行"（不同群用不同模型/人设/工具集）知客只做到"人设按会话绑定"，模型与工具集仍是全局。列为下一轮候选。

#### 5. chatgpt-on-wechat 类项目（同类形态，社区广泛使用）

- **定位**：微信/QQ 个人号接入 ChatGPT。
- **强项**：极简部署、插件化、多模型。
- **弱项**：无权限模型、无审计、无 RAG 工程化、群聊体验粗糙。
- **与知客的关系**：知客在每一项工程能力上都更强；这类项目的优势只有"上手 5 分钟"。知客本轮通过 `.env` 自动加载 + 免 Key 搜索把上手成本也压下来了。

### C 组：自托管 AI 前端

#### 6. Open WebUI（open-webui/open-webui，约 157k stars）

- **定位**：自托管 AI 聊天前端 + RAG + 工具。
- **强项**：9 种向量库；Tika/Docling/OCR 多路文档抽取；Filters/Actions/Pipes/Tools/Skills 五类扩展点；RBAC 细到模型级；OTel 全链路；Redis 多节点。
- **弱项**：它是"人对着 UI 用 AI"，不是"AI 在群里跟人相处"；无 IM 渠道；无动作审批。
- **可借鉴并已落地**：OTel 追踪（原有 `core/tracing.py`，本轮补了指标直方图与请求 ID，形成 metrics+logs+traces 三件套）；文档抽取质量（本轮用 trafilatura 替换正则）。
- **差距**：RBAC 粒度。知客只有 admin/operator/agent/qq 四类主体，没有"按用户/组授权某个模型或知识库"。**判断：个人助理场景不需要，团队版再说。**

#### 7. Chatwoot（chatwoot/chatwoot，约 38.5k stars）

- **定位**：开源客服平台（多渠道收件箱 + 坐席协作）。
- **强项**：全渠道收件箱；自动分配与坐席容量；canned responses、私有备注、@提及；CSAT 报表；自动化与 Captain AI。
- **弱项**：AI 是附加功能，不是核心；无 Agent 工具执行；无本地知识库检索工程。
- **与知客的关系**：知客的"协作台"（接管队列、内部备注、快捷话术、SLA 首响、答案回流 KB）就是 Chatwoot 的对标实现，且**多了一层"机器人先答、答不好才转人"**。
- **差距**：知客没有 SLA 违约告警（只记录 `first_response_seconds`）、没有坐席容量路由。**本轮未补**：无人工坐席的部署下这些是空功能，`USER_HANDOFF_ENABLED=0` 时不该出现。

## 四、优势核查：声称的能力是否真的落地

逐条对照 README 与代码，本轮实测结论：

| 声称 | 核查方式 | 结论 |
|---|---|---|
| 原生 function calling + JSON 降级 | 读 `core/llm.py:_post_chat` 四级降级链 | ✅ 真实实现，且有回归 |
| ReAct 多步 + 五维预算 | `agent_loop.py` + `test_agent_loop.py` 26 例 | ✅ 真实；本轮修了墙钟边界 |
| MCP server 暴露工具 | `core/mcp_server.py` 双代 SDK 适配 | ✅ 真实，但需手动 `pip install -r requirements-mcp.txt` |
| FTS5 + 向量 + RRF | `retrieval.py` + 索引重建/降级链 | ✅ 真实；向量需可选依赖 |
| 42 个工具 | `/api/agent/health` 返回 `tool_count=42` | ✅ 真实（e2e 实测） |
| 语音收发 | `asr.py` + `tools.py:tool_send_voice` | ✅ 代码完整；需可选依赖 |
| 乒乓循环护栏 | `gateway/loop_guard.py` + e2e 脚本 | ✅ 真实，默认开 |
| L0/L1/L2 × T0–T3 权限 | `core/actions/authz.py` + `registry.py` | ✅ 真实，L2 硬编码强制审批 |
| 哈希链审计可校验 | `/api/admin/audit/verify` | ✅ 真实（e2e 覆盖） |
| 中英双语界面 | `locales/en.ts` + `t()` | ⚠️ **部分**：373 处 `t()`，但仍有 1025 处硬编码中文，覆盖率约 36% |
| 814 条测试 | 实测 | ✅ 实际 811 passed + 7 skipped |
| 免 Key 可跑 | 本轮实测（无 Key + rule 模式） | ✅ 修复后成立（此前 QQ 渠道不成立） |

**发现的两处"声称但未落地"**：
1. `.env` 配置项：文档写了 30+ 环境变量，但代码从未加载 `.env`（C1）。
2. QQ 渠道的"无 Key 可跑"：README 说可以，实际被 `no_model` 静默（C2）。

## 六、一句话总结

知客的护城河不是"功能多"，而是**在一个 QQ 群里长期活着所需的全部脏活**：记忆、提醒、权限、审计、人格、防互刷、无模型降级。这些在大平台上是"企业版功能"，在知客里是默认行为。本轮改造补的是**工程可信度**（配置真生效、指标可观测、搜索真能用、正文真干净），而不是去追平台化的功能数量。
